# Insights — Improvement & Growth Plan

> Package: capell-app/insights · Kind: extension (admin + frontend) · Tier: premium · Product group: Capell Growth · Bundle: growth · Status: Draft

## 1. Snapshot

Insights is a first-party, consent-aware web-analytics extension for Capell. The frontend surface ships a vanilla JS tracker injected via a `RenderHookLocation::BodyEnd` hook (`src/Support/RenderHooks/RegisterInsightsTrackerHook.php`) plus two public POST endpoints (`src/Http/Controllers/InsightsBeaconController.php`, `InsightsConsentController.php`) backed by Actions (`RecordInsightsEventsAction`, `ValidateInsightsBeaconRequestAction`, `UpdateInsightsConsentAction`, `CreateInsightsVisitAction`, `MirrorInsightsConsentToPrivacyCenterAction`). The admin surface adds an `InsightsPage`, six dashboard widgets, three overview stats, and a settings schema, fed by `Build*QueryAction` aggregates over three tables (`insights_visits`, `insights_consents`, `insights_events`). Deps: `lorisleiva/laravel-actions`, `spatie/laravel-data`, `spatie/laravel-package-tools`; requires `capell-app/admin|core|frontend`, supports `capell-app/privacy-center`.

Current marketplace summary (verbatim): _"Insights records first-party visits, events, consent decisions, page views, clicks, and journey data for Capell sites."_ The manifest lists **1 screenshot** (`docs/assets/marketplace/extension-card.jpg`) while the repo commits **10 PNG screenshots** under `docs/screenshots/` plus a 5-entry `docs/screenshots.json` — a mismatch (manifest under-references the available media).

## 2. Improvements (existing functionality)

- **Make the JS tracker bootstrap a visit on first hit** — Today the tracker reads `visit_id` only from cookie/localStorage (`resources/js/capell-insights.js:26-52, 116`). A visit row is created _only_ by the consent endpoint (`UpdateInsightsConsentAction::resolveVisit` → `CreateInsightsVisitAction`). So a first-time visitor's initial `page_view` posts with `visit_id: null`, `RecordInsightsEventsAction` finds no visit and returns empty (`src/Actions/RecordInsightsEventsAction.php:34-38`). Add a server "start visit" step (return a fresh `visit_id` from the events endpoint when none supplied and region permits) so out-of-region/no-consent-required traffic is captured. — beacon currently silently drops first views — `src/Actions/RecordInsightsEventsAction.php`, `resources/js/capell-insights.js` — M
- **Derive `hash_salt` from `APP_KEY` by default** — config ships a literal salt `'capell-insights'` (`config/capell-insights.php`), and `CreateInsightsVisitAction::hashSalt()`/`UpdateInsightsConsentAction::hashSalt()` fall back to it. A committed, public salt makes IP/UA HMACs reversible by anyone with the source. Default to `hash_hmac(..., config('app.key'))` and treat the config salt as an optional override. — privacy hardening — `config/capell-insights.php`, `src/Actions/CreateInsightsVisitAction.php`, `src/Actions/UpdateInsightsConsentAction.php` — S
- **Wire `ConsentRegionResolver` into visit creation** — The GeoIP resolver and `ResolveConsentRegionAction` exist and are unit-tested but have **no production caller** (`ResolveConsentRegionAction` is referenced only by its own test; `CreateInsightsVisitAction` takes region as a parameter and both controllers pass the client-supplied `region`). Call `ResolveConsentRegionAction::run()` server-side instead of trusting the request body. — fixes attacker-controllable GDPR jurisdiction + removes dead code — `src/Http/Controllers/InsightsConsentController.php`, `src/Actions/CreateInsightsVisitAction.php`, `src/Support/Consent/ConsentRegionResolver.php` — M
- **Chunk the retention purge** — `PurgeInsightsDataAction::handle` issues unbounded `delete()` on three tables (`src/Actions/PurgeInsightsDataAction.php:22-33`). On a high-write events table this is a long lock / replication-lag risk and conflicts with the analytics scale the package advertises. Delete in `chunkById`/`limit` loops. — perf/lock safety — `src/Actions/PurgeInsightsDataAction.php` — S
- **Cache dashboard aggregates** — `InsightsPage` renders six widgets (`src/Filament/Pages/InsightsPage.php:57-68`), each Action running 2 grouped scans over `insights_events` (`BuildPopularPagesQueryAction`, `BuildTrendingPagesQueryAction`, etc.), plus three overview-stat queries in `AdminServiceProvider::registerOverviewStats`. That is ~12+ full GROUP BY scans per dashboard load with `cacheSafety.cacheable:false` and no rollup. Add short-TTL caching keyed by window+site, invalidated on the `insights` cache tag. — `adminQueryBudget:40` realism — `src/Filament/Pages/InsightsPage.php`, `src/Actions/Build*QueryAction.php` — M
- **Reconcile registered vs on-disk migrations** — `InsightsServiceProvider::configurePackage` registers `2026_05_10_190855_06_add_page_url_hit_columns` and `2026_05_21_000001_add_site_foreign_keys_to_insights_tables` (`src/Providers/InsightsServiceProvider.php:37-44`), but neither file exists (`database/migrations/` holds only `01,02,03,05`). The events table already defines its `site_id` FK inline (`..._03_create_insights_events_table.php`), so the site-FK migration looks redundant; the hit-columns migration is simply missing. Remove the phantom names or commit the files. — fresh-install hazard — `src/Providers/InsightsServiceProvider.php`, `database/migrations/` — S
- **Flesh out the health check** — `InsightsHealthCheck` implements only `compatibleCapellApiVersion()` (`src/Health/InsightsHealthCheck.php`); it is a stub that proves nothing about runtime health. Probe: tables present, routes registered, render hook bound, purge schedule attached, and a non-default `hash_salt` in production. — Diagnostics value — `src/Health/InsightsHealthCheck.php` — M
- **Add a session/sequence reset for page views** — `RecordInsightsEventsAction` computes `sequence` from `max(sequence)+1` per visit and never resets, so a returning visitor's "journey" spans all historical sessions as one timeline (`src/Actions/RecordInsightsEventsAction.php:42`, consumed by `BuildJourneyTimelineAction`/`BuildRecentJourneysQueryAction`). Introduce a session boundary (e.g. 30-min inactivity) so journeys are per-session. — journey accuracy — `src/Actions/RecordInsightsEventsAction.php`, `src/Actions/BuildJourneyTimelineAction.php` — M

## 3. Missing Features (gaps)

Tied to `capabilities[]` = `insights, insights-admin, insights-frontend, insights-privacy-center-mirror, beacon, cache-blocking`.

- **Shipped consent banner / opt-in UI (table-stakes).** The package exposes `window.CapellInsights.consent()` and a consent endpoint but ships **no banner** (grep for `banner`/`CapellInsights.consent` in `src`/`resources` is empty). For UK/EU visitors nothing is recorded until _something_ the host wrote calls consent. A minimal, themable banner (or a Capell frontend component alias) would make the `insights-frontend` capability usable out of the box.
- **Referrer & UTM analytics (table-stakes).** `insights_visits` stores `referrer_url`, `utm_source/medium/campaign` (migration 01) but no Action surfaces them — there is no referrers report, no channel/source breakdown, no campaign attribution. This is core web-analytics and the data is already captured.
- **Pre-aggregated rollups / retention tiers (differentiator).** All reports scan raw `insights_events`. A daily rollup table (path × day × type counts) would unlock fast long-range dashboards and let raw events be purged sooner than aggregates — directly addressing the write-volume budget.
- **Funnels & conversions (differentiator).** Event model supports `event_name`/`label`/custom events, but there is no funnel definition or conversion-rate reporting. High-value for the Growth group and a cross-sell hook for campaign-studio.
- **Bot / self-traffic filtering (table-stakes).** No user-agent bot filtering and no admin/staff exclusion beyond path ignores; analytics quality suffers without it.
- **Visit duration / bounce / entry-exit (table-stakes).** `started_at`/`last_seen_at` exist on the visit but no engaged-time, bounce-rate, or entry/exit-page metrics are computed.
- **Consent expiry & re-prompt (compliance differentiator).** `policy_version` is stored per consent but nothing re-prompts when the version bumps; GDPR best practice is periodic re-consent.
- **Server-side event API surface for other packages.** `RecordCustomActionAction` is documented but only reachable in-process; an authenticated internal contract (so seo-suite/campaign-studio can record conversions) would make `insights` the analytics backbone the bundle implies.
- **Do-Not-Track / Global Privacy Control honoring (differentiator).** No DNT/GPC header check in the tracker or beacon validation.

## 4. Issues / Risks

- **First-visit data loss (functional bug).** See §2 item 1. Every beacon test pre-creates a visit via factory (`tests/Feature/Events/InsightsBeaconControllerTest.php:158-167` etc.), so the no-visit path is never exercised end-to-end — the gap is masked by tests.
- **Client-trusted GDPR region (privacy/integrity).** `InsightsConsentController` builds region from `$validated['region']` and `RecordInsightsEventsAction::canRecordForVisit` keys consent enforcement off the stored `consent_region` (`src/Actions/RecordInsightsEventsAction.php:134-148`). A client can send `outside_uk_or_europe` to bypass consent gating. The GeoIP resolver that would fix this is unused (dead code).
- **Reversible visitor hashes (PII).** Default `hash_salt` is the public literal `'capell-insights'` (`config/capell-insights.php`); raw IP/UA are HMAC'd but with a known salt they are reversible/linkable. Docs flag "set `hash_salt` before production" (`docs/tracking-and-consent.md:101`) but a sensible default + health-check enforcement is missing.
- **Cache-safety of the beacon: OK, with one note.** The render hook output is static config + a file-read script cached `rememberForever` keyed by file mtime (`src/Actions/GetInsightsTrackerScriptAction.php`); the blade does no DB query and leaks no model IDs/labels/permissions (`resources/views/tracker.blade.php`) — consistent with `cacheSafety.cacheable:false, sensitiveOutput:false`. Note: the tracker renders on **every** frontend page with no admin-path guard at render time; suppression relies on server-side `ignored_paths` at record time, so admin/Livewire pages still emit the script tag (harmless but wasteful, and `cache-blocking` is asserted as a capability without an explicit no-store header on the beacon responses).
- **Migration drift (deploy risk).** Two registered migrations have no files; README "Data And Persistence" documents `04_add_insights_reporting_indexes` and `06_add_page_url_hit_columns` that do not exist. `InsightsMigrationsTest` only asserts the three tables exist, so it passes despite the drift.
- **Manifest mismatches (discoverability).** `capell.json`: `settings: []` though `InsightsSettingsSchema` defines ~14 fields and `InsightsSettings` is registered; `permissions: []` though `InsightsPage` uses `HasPageShield` (Shield generates a page permission); `commands.doctor: null` though a (stub) health check exists; `marketplace.screenshots` references 1 image while 10 PNGs + `screenshots.json` are committed.
- **Dead / parallel code (tech debt).** Single-event family `RecordInsightsEventAction`/`RecordPageViewAction`/`RecordClickAction`/`RecordCustomActionAction` is not on the request path (controller uses `RecordInsightsEventsAction`, plural); `ImportLegacyPageViewsAction` is invoked only from a migration + test; `ResolveConsentRegionAction`/`ConsentRegionResolver` have no production caller.
- **Performance budget realism.** `frontendRenderBudgetMs:20` is plausible (cached script), but `adminQueryBudget:40` is unrealistic for the 6-widget page hitting raw events with no rollup/cache (§2). High write volume on `insights_events` + non-chunked purge (§2) is the principal scaling risk.
- **i18n.** Strings are translated via `capell-insights::` keys (good), but the config key `track_form-builder` contains a hyphen and is mirrored as a setting/label key — brittle and inconsistent with snake_case siblings (`config/capell-insights.php`, `src/Filament/Settings/InsightsSettingsSchema.php:34`).
- **Test gaps.** No test for: first-visit auto-creation, server-side region resolution on the consent path, dashboard query caching, purge chunking, health-check probes, referrer/UTM reporting (feature absent), or render-hook suppression on admin paths. Frontend JS is asserted by string-matching (`tests/Unit/Frontend/InsightsScriptTest.php`) rather than DOM behavior.

## 5. Marketplace & Selling

**Critique.** The manifest `summary` and composer `description` ("First-party insights, visitor journeys, click tracking, and consent management.") both _list mechanics_ and bury the value. Neither says who it's for or why it beats Google Analytics. The summary also leans on jargon ("events, consent decisions … journey data") rather than the buyer benefit (privacy-safe traffic insight without third-party scripts). Media is under-sold: 10 polished light/dark screenshots exist but the marketplace card surfaces only a single generic preview JPG.

**Improved 1-sentence summary.** "Cookie-light, GDPR-aware web analytics built into your Capell admin — page views, clicks, visitor journeys, and consent, with no third-party scripts and no data leaving your server."

**Improved 3–4 sentence description.** "Insights gives Capell sites first-party traffic analytics that respect privacy by default: it records page views, clicks, and visitor journeys server-side, hashes visitor identifiers, and gates UK/EU tracking behind consent. Dashboards for popular pages, trending pages, top actions, and recent journeys live right inside the admin Marketing Studio — no Google Analytics, no cookie soup, no tag manager. Retention windows and an automatic purge keep data lean and compliant. When Privacy Center is installed, consent decisions are mirrored into your central consent ledger automatically."

**Media gaps.** Reference the 10 committed screenshots (and the captioned `screenshots.json`) in `marketplace.screenshots`; add a short "consent flow" capture once a banner ships; add a hero showing the overview stats + a journey timeline.

**Pricing / tier / bundle positioning.** Premium tier in the `growth` bundle is appropriate _if_ the first-visit and consent-banner gaps are closed — as-is the out-of-the-box experience under-delivers for a paid first-party tier. Insights is the natural data backbone of the bundle: position seo-suite and campaign-studio as **dependents** that record conversions/funnels through an Insights server-side contract (cross-sell), and lean on the existing `supports: capell-app/privacy-center` mirror as a compliance upsell. Bundle messaging: "Insights measures it, Campaign Studio acts on it, SEO Suite ranks for it."

**Differentiators / value props / target buyer.** Differentiators: privacy-first (no third-party scripts, hashed identifiers, consent-gated, Privacy Center mirror), fully in-admin, multi-site/locale aware. Target buyer: privacy-conscious agencies and site owners on Capell who want GA-style insight without GA's compliance and cookie overhead.

**Keywords/tags (8–12).** `web-analytics`, `privacy-friendly-analytics`, `gdpr`, `cookie-consent`, `first-party-tracking`, `page-views`, `click-tracking`, `visitor-journeys`, `marketing-studio`, `consent-management`, `filament`, `capell`.
